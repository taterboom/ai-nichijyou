# deepen

人只能把自己想到的事做好。这个 skill 把「认知之外」的东西拉进来：专家的方法、独立的视角、模型和用户之外的评判者。
思路来自 Felix Rieseberg 的 *How to be more ambitious*（深度 / 外部评判者）与 Anthropic 的 Code Review 实践（自证、独立审查、事故变检查）。

## 0. 先判断值不值得

只对这些用：新功能、交互方案、产品 / 商业决策、高风险路径（权限、支付、数据迁移、破坏性操作、发往第三方的内容）。
文案、样式微调、已定位的小 bug 直接做，告诉用户「这个不值得深挖」即可。

## 1. 拿原始素材，不拿结论

先自己读：相关代码、真实数据、用户反馈、已有文档和 lessons。用户给的描述是经过用户自身认知过滤的摘要，只当线索。
记下素材的路径或链接，第 3 步要原样交给子代理。

## 2. 用动词重述，选学科

用一句**动词**描述这件事真正在做什么（例：轮盘不是「一个菜单」，而是「让手不离开鼠标地在上下文之间跳转」）。
从这句话里挑 3–5 个最相关的学科，产品侧与代码侧都要考虑：

- 产品：交互 / HCI、行为与习惯、商业与定价、增长与分发、平台政策
- 代码：正确性、安全与隐私、性能、可维护性、UI / UX 实现

挑出能改变做法的学科，不要凑数。

## 3. 并行派独立子代理

每个学科一个子代理，**同一条消息并行发出**，各自是全新上下文（不继承本对话的假设）。给每个子代理：

- 任务的一句话目标 + 第 1 步的原始素材路径（不要给你的分析）
- 下面这段要求，原样附上：

> 我要的是这件事更深的版本，而不是更大的版本。请从「{学科}」顶尖从业者的实际工作方式出发回答：
> 1. 他们会做、但任务里没要求的事是什么？
> 2. 他们会从哪些最原始的素材入手，而不是别人整理好的结论？
> 3. 他们会用哪些具体的方法、工具、度量？（说出名字，不要泛泛而谈）
> 4. 除了作者和 AI 之外，什么东西能证明结果是对的？（测试、真实环境、数据、用户、权威来源）
> 5. 这件事最可能以什么方式失败？
>
> 做他们会做的事，不要扮演他们、不要模仿语气。每条都要具体到可执行；区分「有来源的事实」和「你的推测」。每题最多 3 条。

## 4. 汇总并改写任务

去重；丢掉泛泛的建议（「加测试」「注意性能」这类没有具体对象的）；只保留**会改变做法或验证方式**的条目。按下面格式给用户：

```
## 深挖：<任务>
一句话（动词）：...

### 你没要求、但专家会做的
- ...（来自哪个学科）
### 该从哪些原始素材入手
- ...
### 具体方法与工具
- ...
### 外部评判者（怎么证明做对了）
- ...
### 最可能的失败方式
- ...

### 改写后的任务
<更深、可验证的版本；包含一个有野心但可度量的目标，以及完成的判定标准>
```

然后请用户勾选采纳哪些条目。采纳的内容进入计划（项目用 `tasks/todo.md` 就写进去），未采纳的不要偷偷实现。

## 5. 收尾：把盲区固化下来

做完之后（或用户在复盘、修 bug 时调用），对每个这次才暴露出来的盲区问一句「哪一层本该拦住它」，然后按优先级固化：

1. 能机器检查 → 测试、fixture、lint / check 脚本里的规则（并反向验证它真能拦住）
2. 机器查不了的硬规则 → 项目 `CLAUDE.md` 里一行
3. 其余经验 → `tasks/lessons.md`

宁可一条能跑的检查，也不要一段需要人记住的文字。
