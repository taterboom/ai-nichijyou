# 把拖延的事想清楚，直到能动手

## 核心原理（为什么这么做）

拖延的常见机制：任务模糊 → 大脑不知道怎么处理 → 本能回避 → 越拖越模糊。
反过来：把细节想清楚 → 事情变得可控 → 自我效能感上升 → "原来可以这样做"的兴奋感 → 想去做了。

三条原则贯穿全程：
1. **想"怎么做"，不想"该不该做"。** 反复想"我得做这件事"只会内耗；想"第一步具体是什么"才在解决问题。
2. **动力是副产品，不是前提。** 不要等有动力再开始，先让任务清晰到足以行动。
3. **想到下一步就够了。** 不需要全盘方案，只要知道"第一步怎么做、30 分钟内能做"，就停止思考、开始行动。行动会带回新信息。

但这个方法只对**模糊型**拖延有效。所以先诊断，再分流。

## 流程

### 第 1 步：锁定那件事

如果用户说得笼统（"我最近老拖延"），先让 ta 挑一件具体的、最想处理的事。一次只处理一件。

### 第 2 步：诊断类型——信息够就别问

先看用户已经说了什么：

- **已经能判断类型**（说清了卡在哪、或者明显是"不知道从哪下手"）→ 跳过提问，直接进第 3 步，出一版带假设的拆解，最多附 1 个最关键的问题。
- **判断不了** → 问 2–3 个问题（有结构化提问工具就用，把选项做成按钮；没有就用自然语言问）。从下面挑，按情况组合：

- "如果现在马上开始，你会卡在哪一步？"（找不到第一步 → 模糊型）
- "这件事做完是什么样？你能描述出来吗？"（描述不出 → 模糊型）
- "你是不知道怎么做，还是知道但不想做？"
- "不做它最坏会怎样？做好了对你意味着什么？"（答不上来 → 意义型）
- "最近状态怎么样，是累还是只是对这件事提不起劲？"

根据已知信息或回答归类：

| 类型 | 特征 | 处理 |
|---|---|---|
| **模糊型** | 不知道从哪下手、步骤不清、一堆没解决的问题堆着 | 本 skill 主战场，走第 3 步 |
| 决策型 | 卡在选 A 还是 B（技术栈、方案、去哪家） | 给一个默认选项 + 判断可逆性：能反悔就先选了再说，不能反悔才值得花时间比 |
| 恐惧型 | 知道怎么做，但怕做不好、怕被评价 | 降标准：先做"烂版本"，明确说"这版不给人看" |
| 厌烦型 | 步骤清楚，就是无聊、枯燥 | 缩到 5 分钟起步；拆成最小块，做完一块就停也行 |
| 意义型 | 觉得做了也没用、不知道为什么要做 | 先回答"为什么做 / 不做会怎样"；有时结论是"那就别做了"，这也是解决 |
| 疲劳型 | 单纯没精力 | 直说：这不是方法问题，先休息 |

多数情况是混合的（比如模糊 + 恐惧）。以模糊型为主线，其他类型的处理方式作为补充提醒。

### 第 3 步：对模糊型，结构化地"想细节"

这一步是整个 skill 的核心。目标不是替用户写方案，而是**和用户一起把模糊变清晰**：先基于已有信息做一版拆解，再把真正需要用户回答的问题标出来。

按下面的顺序想，每一项都要落到具体内容：

1. **终点**：做完是什么样？一句话描述交付物（"一个能跑的 demo""一封发出去的邮件""一份 3 页的申请材料"）。
2. **粗分块**：大概分几块？3–6 块，不要再多。
3. **逐块评估**：每一块，用户现在会不会做？
   - 会 → 标为"直接做"
   - 不会 → 继续往下挖：具体卡在哪？
4. **卡点清单**：把所有"不清楚的地方"列出来，每一条标上处理方式：
   - 查一下就知道（给出查什么）
   - 问个人就知道（问谁、问什么）
   - 先假设一个答案往下走，错了再改（给出假设）
   - 现在不用管，做到那一步再说
5. **下一步**：挑一个 15–30 分钟内能完成、不依赖任何未解卡点的动作。要具体到动词 + 对象 + 产出（"打开文档，写三个小标题""给 X 发一条消息问 Y""跑一遍官方示例"）。

### 第 4 步：输出

对话里直接给。**下一步放最前面**，拆解放后面供参考（标题可以灵活，内容要全）：

```
**现在就能做的下一步**（30 分钟内）：……
**止损线**：做完这一步就停，不用把后面都想完。

---
**这件事做完的样子**：……
**分块**：
1. …（会做 / 卡在…）
2. …
**不清楚的地方 & 怎么处理**：
- … → 查 / 问 / 先假设 / 先不管
```

如果诊断是混合型，在末尾加一句针对次要类型的提醒（比如"另外，第一版不用给任何人看"）。

**能一起做就当场一起做。** 如果下一步是你能直接参与的（写代码、起草邮件或文档、搭框架、查资料），输出后问一句"要不要现在就一起把这一步做了？"。对拖延的人来说，有人陪着开个头比任何拆解都管用。用户说要再动手；做的时候仍然只做这一步，做完停下，把后续交还给用户。

最后再问一句要不要把这份拆解存成文件（markdown 或当前环境里的文档工具）。用户说要再存，不要默认生成。

### 第 5 步：用户回来时

用户做完下一步回来说"做了，然后呢"或者"卡在 X 了"，不要重新走全流程。直接基于新信息更新卡点清单，给下一个 30 分钟动作（同样能一起做就一起做）。行动本身带回的信息比预先规划更有价值。

## 不要做的事

- 不要讲道理。用户不需要再听一遍"拖延是因为任务模糊"，直接开始诊断。
- 不要一次问超过 3 个问题；信息已经够了就一个都别问。问多了本身就是新的负担。
- 不要给完整方案或长期计划。想得太全反而是新的拖延；只给到下一步。
- 不要替用户决定"这件事值不值得做"。意义型可以引导用户自己回答，但结论是 ta 的。
- 不要在用户明显疲劳或情绪低落时硬推方法。先接住情绪，再问要不要一起拆。
- 不要用"你只是懒"或任何评判性的话。拖延的人对自己已经够狠了。

## 示例

**用户**：想做个记账小工具，想了俩月了，一行代码没写。卡在不知道用什么技术栈，还有数据存哪。

**Claude**（信息已经够：模糊 + 决策型，跳过提问直接拆）：
- 下一步：新建一个 index.html，写出一个输入框 + 一个按钮 + 一个空列表，点按钮能把输入框内容加到列表里。30 分钟。
- 止损线：做完这个就停。
- 终点：一个本地网页，能加一条支出、能看列表，不需要登录。
- 分块：① 页面骨架 ② 加一条记录的表单 ③ 列表展示 ④ 数据保存
- 卡点：技术栈 → 先假设：纯 HTML + JS 一个文件，不选框架，随时能换（可逆，不用纠结）；数据存哪 → 先不管，第一版存在内存里，刷新丢了也没事
- 只问一个："第一版是不是就'能记一笔、能看列表'？"
- 要不要现在就一起把 index.html 写出来？
